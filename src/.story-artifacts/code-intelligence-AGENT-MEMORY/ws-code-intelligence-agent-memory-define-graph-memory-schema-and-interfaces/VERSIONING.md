# Versioning Rules — Code Knowledge Graph Schema

## Overview

The code knowledge graph schema follows a **Major.Minor** versioning scheme
defined in `SchemaVersion`. All serialized graph documents embed their
schema version so consumers can check compatibility at read time.

## Rules

| Change kind | Version bump | Examples |
|---|---|---|
| **Breaking** | Major | Removing or renaming a field; changing the meaning of an existing enum value; altering the canonical ID format; removing a node/edge kind. |
| **Additive** | Minor | Adding a new optional field; adding a new `NodeKind` or `EdgeKind` enum member; adding new metadata keys. |

## Compatibility contract

1. **Consumers must tolerate unknown JSON properties** — ignore them.
   `GraphJsonDefaults.Options` sets `JsonUnmappedMemberHandling.Skip` to
   silently ignore unknown properties during deserialization. The JSON Schema
   does not use `additionalProperties: false` on any type, so unknown
   properties also pass schema validation.
2. **Consumers must handle unknown enum string values** — the
   `LenientEnumConverter<T>` deserializes unrecognized strings to `Unknown`
   (`default(T)`). Consumers using custom deserialization must replicate
   this behavior; `JsonStringEnumConverter` will throw on unknown values.
   The JSON Schema defines enum kinds as `type: "string"` with known values
   listed in `examples` (not a strict `enum` constraint), so unknown values
   pass schema validation.
3. **Producers must never emit `Unknown`** as a node or edge kind.
   `Unknown` is excluded from the JSON Schema examples.
4. **Wire format** — all enum values are serialized as **camelCase strings**
   by `LenientEnumConverter<T>`, not integers.
5. **Null-valued optional fields are omitted**, not serialized as `null`.
   This is enforced by `JsonIgnoreCondition.WhenWritingNull` in
   `GraphJsonDefaults.Options`. The JSON Schema models these fields as
   optional (not required) with non-nullable types.
6. **ID stability** — once a canonical ID format is established for a major
   version, it must not change within that major version. IDs are based on
   qualified names and may change when symbols are renamed or moved; consumers
   should treat this as the node being deleted and recreated.
7. **Compatibility check** — use `SchemaVersion.IsCompatibleWith(other)`:
   same major version and `other.Minor >= this.Minor` ⇒ compatible.

## JSON Schema Generation

The JSON Schema is generated from the C# model by recursively walking
`System.Text.Json.Serialization.Metadata.JsonTypeInfo` obtained from
`GraphJsonDefaults.Options` (see `JsonSchemaGenerator.cs`). Types are
discovered automatically starting from `CodeKnowledgeGraph` — no hardcoded
type list is maintained. Adding a new property or record to the model
automatically updates the schema. The generator throws
`NotSupportedException` for any unsupported CLR type, preventing silent
schema drift.

The committed schema file at
`schema/code-knowledge-graph.schema.json` is generated by running
`dotnet run --project tools/GenerateSchema`. A test
(`CommittedSchemaFile_MatchesGenerator`) enforces that the committed
schema matches the generator output.

## Canonical Node ID Format

| Kind | Pattern | Example |
|---|---|---|
| Repo | `repo:{name}` | `repo:my-service` |
| Module | `module:{repo}:{dotted.namespace}` | `module:my-service:MyApp.Services` |
| File | `file:{repo}:{forward/slash/path}` | `file:my-service:src/Foo.cs` |
| Class | `class:{repo}:{qualified.name}` | `class:my-service:MyApp.Foo` |
| Function | `function:{repo}:{qualified.name}:{sig-hash}` | `function:my-service:MyApp.Foo.Bar:a1b2` |
| Variable | `variable:{repo}:{qualified.owner}:{name}` | `variable:my-service:MyApp.Foo:_count` |

### Normalization

- Paths use forward slashes, lowercase on case-insensitive file systems.
- Qualified names use dots as separators.
- Signature hashes are stable across identical parameter lists.

### ID Stability Caveats

- IDs are name-based and will change on symbol rename, file move, or
  namespace refactor. When this happens the old node ceases to exist and a
  new node is created; graph consumers must handle this gracefully.
- Lambdas and anonymous symbols do not have canonical IDs in v1.x;
  producers should omit them or use a producer-specific convention stored
  in the PropertyBag.

## Edge Semantics

- All edges are **directed** (source → target).
- Duplicate edges with the same (source, target, kind) are allowed when
  properties differ (e.g. multiple call sites).
- `Weight` is optional; when present it must be in **[0.0, 1.0]**.
- `Expertise` edges represent agent-learned relationships and are expected
  to carry a `Weight` (missing weight produces a validation warning).
- `SimilarTo` edges **must** carry a `cosine_similarity` property in the
  PropertyBag, a number in [0.0, 1.0]. If `Weight` is also present, it
  should equal `cosine_similarity` (mismatch produces a validation warning).
- **Self-loops** (source == target) are rejected for structural edge kinds:
  Contains, Calls, Imports, Inherits. They are permitted for Expertise and
  SimilarTo.

## Endpoint Type Constraints

The `GraphValidator` enforces pairwise endpoint constraints for structural
edge kinds. The rules are defined in `GraphValidator.EndpointRules`:

| EdgeKind | Allowed Source → Target |
|---|---|
| Contains | Repo → {Module, File}, Module → {File, Module}, File → {Class, Function, Variable}, Class → {Function, Variable} |
| Calls | Function → Function |
| Imports | File → {File, Module}, Module → {File, Module} |
| Inherits | Class → Class |
| Expertise | (any → any) |
| SimilarTo | (any → any) |

## PropertyBag Key Restrictions

Property bag keys must match the pattern `^[a-zA-Z][a-zA-Z0-9_.]*$`:
- Start with a letter
- Followed by letters, digits, underscores, or dots
- Dots enable namespace-style grouping (e.g. `neo4j.label`)

This restriction is enforced at runtime by `PropertyBag.ValidateKey()`
and in the JSON Schema via `propertyNames.pattern`.

## SourceLocation Validation

The `GraphValidator` enforces:
- Line and column numbers must be non-negative (when present).
- `EndLine` must be ≥ `StartLine` (when both present).
- `EndColumn` must be ≥ `StartColumn` when on the same line.

## SchemaVersion Validation

`Major` and `Minor` must both be non-negative integers.
